# Rules for every agent. Read this file first, then your role file `.claude/agents/<role>.md` (short: domain and test files).

## Start here (at most 4 reading calls before you work)

1. **The command.** The owner writes `<role>: <task>` (the colon is optional). `<task>` is: a number (`003`, `task 003`, `#003`) = the spec file `tasks/003-*.md` (list the folder `tasks` once to get the file name); or a path `tasks/003-x.md`; or free text (the text is the task; for `-tdd` and `-dev` write its acceptance criteria in 3 to 5 lines first); or `MR !n` (gatekeeper).
2. **The repository.** GitLab project `bellaabrahamyan.am/ahm` (id 88632181), trunk branch `master`. The repository root IS the extension: there is no `ext/` folder. Where things are: `tasks/NNN-*.md` task specs, `context/<domain>.md` your file list and reading list, `changes/<domain>.md` log, `todo/<domain>.md`, `proposals/`, `requests/`, `tools/domains.json` file owners, `.claude/agents/` roles, `app/js/<domain>/` and `tests/` code. Tasks are plain files: never search issues, work items or wikis, and never look for `ext/ahm/map/`.
3. **Old documents.** Anything else you were given (Project documents, earlier briefs) that mentions `ext/ahm/map/`, GitHub, `gh`, `add_repo`, cloning from GitHub or pull requests is OLD. This file and your role file win.
4. **How to reach the code. Decide once, with ONE test:** `git ls-remote https://gitlab.com/bellaabrahamyan.am/ahm.git master`.
   - *It answers:* you have git. Clone once (`git clone --depth 50 https://gitlab.com/bellaabrahamyan.am/ahm.git`), branch from `master`, run the tests locally (rule 7), push. A private project and every push need a token: use the one in the Project files if there is one (never print it, never commit it); without a token, commit with `add_commit` instead.
   - *It fails* (`could not resolve host`, `CONNECT tunnel failed, 403`): gitlab.com is blocked in this chat. Do not retry or probe. Use the GitLab tools only: ONE `tool_search` call with the query `gitlab repository file commit merge request pipeline` (in Claude Code: ToolSearch). CI is then your test run. The owner can allow `gitlab.com` in the chat's network settings to get git back.
5. **GitLab tools** (always `project_id: bellaabrahamyan.am/ahm`): read a file `get_repository_file` (`file_path`, `ref`, optional `offset` and `limit` in lines); list a folder `list_repository_tree` (`path`, `ref`); new branch `add_branch` (`branch`, `ref: master`); commit `add_commit` (`branch`, `commit_message`, `actions`; at most 100 per call; `create` with `content`, `update` with `old_str`/`new_str`, `delete`); merge request `save_merge_request`; pipelines `list_pipelines` (`per_page`), `get_pipeline` (`include: ["jobs"]`), `get_job` (`include: ["log"]`, `from: "end"`, `byte_limit: 6000`); open merge requests `list_merge_requests` (`state: opened`).
6. **Finish every answer with the owner's next command** on one line, for example: Next: `sidebar-dev: task 003`.

## Rules

1. English only. First line of every answer: `Domain: <your domain>`. Short and concrete answers; no pasted files or test output.
2. Read `context/<domain>.md` and ONLY the files it lists. If `tools/prompts/domain/<domain>.md` exists, read it too (domain notes; its "Git delivery" part is replaced by this file). Then read the task spec. Do only what the task asks.
3. One task = one branch = one merge request (MR). The branch name is the `Branch:` line of the spec (normally `<domain>/<task>`). Never push or commit to `master`. The `-tdd` agent creates the branch and pushes it, the `-dev` agent continues on it.
4. Commits read `<type>: <what>` (`test:`, `feat:`, `fix:`, `docs:`). End each commit message with the Co-Authored-By and Claude-Session lines your environment gives you.
5. Change only your domain's files (table: `tools/domains.json`). With git, check before pushing: `node tools/ci-check-pr.js <branch> origin/master` (the CI job `domain` checks it again). Anything outside your domain: write `requests/<from>-to-<to>-NNN-<name>.md` (fits the interface) or `proposals/NNN-<name>.md` (changes an interface) and stop that part. Interfaces and shared files change only with the owner's approval.
6. Log the change in `changes/<domain>.md` in the same merge request (date, what, why, files, how to verify, follow-ups).
7. Tests. With git: run them locally before every push, output cut: `php tests/php/run.php 2>&1 | tail -15`, `php tests/data/run.php 2>&1 | tail -15`, `node tests/js/run.js 2>&1 | tail -15` (`--no-browser` is quicker). Without git: CI is the test run (rule 9). Never weaken, delete or edit a test you did not write for this task.
8. Merge request: only the `-dev` agent opens it, when its code is pushed (and, with git, passes locally): `save_merge_request` (`project_id`, `source_branch`, `target_branch: master`, `title: <type>: <what>`, `description` = `.gitlab/merge_request_templates/Default.md` filled in, `squash: true`, `remove_source_branch: true`). The `-tdd` agent opens none: its tests are red on purpose and a pipeline would only waste CI minutes. `gh` and GitHub are not used any more.
9. CI: after the MR exists wait 150 s, then `list_pipelines` (`per_page: 2`), then every 60 s (up to 10 min) until the newest pipeline is not `created`, `pending` or `running`. It must be `success`. The job `tests` is skipped when only documents changed (the pipeline is then just `domain`). On `failed`: `get_pipeline` (`include: ["jobs"]`) and `get_job` (`include: ["log"]`, `from: "end"`, `byte_limit: 6000`); fix everything you can find, then push once (each push starts a new pipeline).
10. **Only `gatekeeper` merges.** `-dev` agents fix red checks on the same branch, report "MR !n ready for gatekeeper" and stop. Nobody else merges, ever.
11. Keep tool output small (it costs tokens): `per_page` 5 or less in `search` and `list_*`; search only with `filename:` or an exact name, never with a broad word; read files with `offset`/`limit`; do not re-read a file you just changed; ignore the long JSON that `save_merge_request` and `add_commit` return.

## Role `<domain>-tdd` (test-first writer)

Read `context/<domain>.md` and the task spec. 1) Create the branch named in the spec (`Branch:` line, normally `<domain>/<task>`) from `master`. 2) Write tests for the acceptance criteria, in your domain's test files only (listed in your role file; a new test file only if the spec names it and `tools/domains.json` has its owner line). 3) With git: run them; they must FAIL, for the right reason. 4) Commit `test: ...` and push the branch. Write NO production code and open NO merge request. Finish: "Red tests pushed on branch <name>: <k> failing (<what they check>). Next: `<domain>-dev: task <NNN>`."

## Role `<domain>-dev` (implementer)

Read `context/<domain>.md` and the task spec. Work on the branch the `-tdd` agent pushed (the spec's `Branch:`); the red tests are your spec. No such branch or no red test: stop and say "Next: `<domain>-tdd: task <NNN>`". Write the minimum production code in your domain until the tests pass; commit `feat: ...` or `fix: ...`; add the entry in `changes/<domain>.md` (and tick the item in `todo/<domain>.md`); push; open the merge request (rule 8); wait for CI (rule 9). Do not edit the tests written by `-tdd`; a test you think is wrong: stop and tell the owner. Finish: "MR !<n> ready for gatekeeper, CI success. Next: `gatekeeper: MR !<n>`."
