# Rules for every agent. Read this file first, then your role file `.claude/agents/<role>.md` (short: domain and test files).

## Start here (at most 4 reading calls before you work)

1. **The command.** The owner writes `<role>: <task>` (the colon is optional). `<task>` is: a number (`003`, `task 003`, `#003`) = the spec file `tasks/003-*.md` (list the folder `tasks` once to get the file name); or a path `tasks/003-x.md`; or free text (the text is the task; for `-tdd` and `-dev` write its acceptance criteria in 3 to 5 lines first); or `PR #n` (gatekeeper).
2. **The repository.** GitHub project `bellaabrahamyanam-alt/ahm` (https://github.com/bellaabrahamyanam-alt/ahm), trunk branch `master`. The repository root IS the extension: there is no `ext/` folder. Where things are: `tasks/NNN-*.md` task specs, `context/<domain>.md` your reading list, `changes/<domain>.md` log, `todo/<domain>.md`, `proposals/`, `requests/`, `tools/domains.json` file owners, `.claude/agents/` roles, `app/js/<domain>/` and `tests/` code. Tasks are plain files: never search issues or wikis, and never look for `ext/ahm/map/`.
3. **Old documents.** Anything else you were given (Project documents, earlier briefs) that mentions `ext/ahm/map/`, GitLab, merge requests or the GitLab tools (`get_repository_file`, `add_commit`, `save_merge_request`, `list_pipelines`) is OLD. This file and your role file win. The old GitLab project is no longer used.
4. **Get the code.** Clone once and branch from `master`: `git clone --depth 50 https://github.com/bellaabrahamyanam-alt/ahm.git` (a shallow clone tracks only `master`: `git fetch origin master` before a rebase). A push needs the credentials of your environment (never print a token, never commit it). If a `gh` call fails with `GraphQL is not available`, use `gh api repos/bellaabrahamyanam-alt/ahm/...` (REST) instead of `gh pr ...`. If git itself is blocked in your environment, say so and stop: do not probe.
5. **Finish every answer with the owner's next command** on one line, for example: Next: `sidebar-dev: task 003`.

## Rules

1. English only. First line of every answer: `Domain: <your domain>`. Short and concrete answers; no pasted files or test output.
2. Read `context/<domain>.md` and ONLY the files it lists (read first, then the part of the code the task needs). If `tools/prompts/domain/<domain>.md` exists, read it too (domain notes). Then read the task spec. Do only what the task asks.
3. One task = one branch = one pull request (PR). The branch name is the `Branch:` line of the spec (normally `<domain>/<task>`). Never push or commit to `master`. The `-tdd` agent creates the branch and pushes it, the `-dev` agent continues on it.
4. Commits read `<type>: <what>` (`test:`, `feat:`, `fix:`, `docs:`). End each commit message with the Co-Authored-By and Claude-Session lines your environment gives you.
5. Change only your domain's files (table: `tools/domains.json`). Check before pushing: `node tools/ci-check-pr.js <branch> origin/master` (the CI job checks it again). Anything outside your domain: write `requests/<from>-to-<to>-NNN-<name>.md` (fits the interface) or `proposals/NNN-<name>.md` (changes an interface) and stop that part. Interfaces and shared files change only with the owner's approval.
6. Log the change in `changes/<domain>.md` in the same PR (date, what, why, files, how to verify, follow-ups).
7. Tests. Run them locally before every push, output cut: `php tests/php/run.php 2>&1 | tail -15`, `php tests/data/run.php 2>&1 | tail -15`, `node tests/js/run.js 2>&1 | tail -15` (`--no-browser` is quicker). Never weaken, delete or edit a test you did not write for this task.
8. Pull request: only the `-dev` agent opens it, when its code is pushed and passes locally. Title `<type>: <what>`, body = `.github/pull_request_template.md` filled in. `gh pr create --base master --head <branch> --title ... --body ...`, or in REST form `gh api repos/bellaabrahamyanam-alt/ahm/pulls -f title=... -f head=<branch> -f base=master -f body=...` (the number is in the answer: `--jq .number`). The `-tdd` agent opens none: its tests are red on purpose and a CI run would only waste minutes.
9. CI: the workflow `ci` (`.github/workflows/ci.yml`, runs `tools/ci.sh`; GitLab's `.gitlab-ci.yml` runs the same script). After the PR exists wait 150 s, then check `gh run list -R bellaabrahamyanam-alt/ahm --branch <branch> --limit 2`, then every 60 s (up to 10 min) until the newest run is not `queued` or `in_progress`. It must be `success`. The job does: domain check, `graph/`, tests; when only documents changed it stops after the domain check. When code changed and `graph/` is stale, the job commits `graph/` to your branch (`chore: update graph/ (generated by CI)`; needs the secret `GRAPH_PUSH_TOKEN`) and the run of that new commit runs the tests: wait for the newest run, and `git pull --rebase origin <branch>` before your next push. On `failure`: `gh run view <run id> -R bellaabrahamyanam-alt/ahm --log-failed | tail -40`; fix everything you can find, then push once (each push starts a new run).
10. **Only `gatekeeper` merges.** `-dev` agents fix red checks on the same branch, report "PR #n ready for gatekeeper" and stop. Nobody else merges, ever.
11. Keep tool output small (it costs tokens): `--jq` and `--limit 5` on every `gh` call; read files with offset and limit; do not re-read a file you just changed; no broad searches. Set the PR title and body right at creation; do not edit a PR afterwards. Make all file changes of a step in ONE commit. One chat per task: start a new chat for the next task, a long chat re-sends every old tool result.

## Role `<domain>-tdd` (test-first writer)

Read `context/<domain>.md` and the task spec. 1) Create the branch named in the spec (`Branch:` line, normally `<domain>/<task>`) from `master`. 2) Write tests for the acceptance criteria, in your domain's test files only (listed in your role file; a new test file only if the spec names it and `tools/domains.json` has its owner line). 3) Run them; they must FAIL, for the right reason. 4) Commit `test: ...` and push the branch. Write NO production code and open NO pull request. Finish: "Red tests pushed on branch <name>: <k> failing (<what they check>). Next: `<domain>-dev: task <NNN>`."

## Role `<domain>-dev` (implementer)

Read `context/<domain>.md` and the task spec. Work on the branch the `-tdd` agent pushed (the spec's `Branch:`); the red tests are your spec. No such branch or no red test: stop and say "Next: `<domain>-tdd: task <NNN>`". Write the minimum production code in your domain until the tests pass; commit `feat: ...` or `fix: ...`; add the entry in `changes/<domain>.md` (and tick the item in `todo/<domain>.md`); push; open the pull request (rule 8); wait for CI (rule 9). Do not edit the tests written by `-tdd`; a test you think is wrong: stop and tell the owner. Finish: "PR #<n> ready for gatekeeper, CI success. Next: `gatekeeper: PR #<n>`."
