# Rules for every agent. Read this file first, then your role file `.claude/agents/<role>.md`.

## Start here (at most 4 reading calls before you work)

1. **The command.** The owner writes `<role>: <task>` (the colon is optional). `<task>` is: a number (`003`, `task 003`, `#003`) = the spec file `tasks/003-*.md` (list the folder `tasks` once to get the file name); or a path `tasks/003-x.md`; or free text (the text is the task; for `-tdd` and `-dev` write its acceptance criteria in 3 to 5 lines in the merge request description); or `MR !n` (gatekeeper).
2. **The repository.** GitLab project `bellaabrahamyan.am/ahm` (id 88632181), trunk branch `master`. The repository root IS the extension: there is no `ext/` folder. Where things are: `tasks/NNN-*.md` task specs, `context/<domain>.md` your file list and reading list, `changes/<domain>.md` log, `todo/<domain>.md`, `proposals/`, `requests/`, `tools/domains.json` file owners, `.claude/agents/` roles, `app/js/<domain>/` and `tests/` code. Tasks are plain files: never search issues, work items or wikis, and never look for `ext/ahm/map/`.
3. **Old documents.** Anything else you were given (Project documents, earlier briefs) that mentions `ext/ahm/map/`, GitHub, `gh`, `add_repo`, cloning or pull requests is OLD. This file and your role file win.
4. **How to reach the code. Decide once, do not probe.**
   - *Claude cloud chat* (a Project chat, no terminal): `gitlab.com` is blocked (`CONNECT tunnel failed, 403`), so do NOT clone, fetch or push. Use the GitLab tools only. Load them with ONE call: `tool_search` with the query `gitlab repository file commit merge request pipeline` (in Claude Code: ToolSearch). Tests cannot run there: the CI pipeline of the merge request is the test run.
   - *A terminal with git access* (your computer, Claude Code): `git fetch origin master && git checkout -b <branch> origin/master`, run the tests, `git push -u origin <branch>`.
5. **GitLab tools** (always `project_id: bellaabrahamyan.am/ahm`): read a file `get_repository_file` (`file_path`, `ref`, optional `offset` and `limit` in lines); list a folder `list_repository_tree` (`path`, `ref`); new branch `add_branch` (`branch`, `ref: master`); commit `add_commit` (`branch`, `commit_message`, `actions`; at most 100 per call; `create` with `content`, `update` with `old_str`/`new_str`, `delete`); merge request `save_merge_request` (create, or update with `merge_request_iid`); state and pipelines `get_merge_request` (`merge_request_iid`, `include: ["pipelines"]`); failed job `get_pipeline` (`include: ["jobs"]`) then `get_job` (`include: ["log"]`, `from: "end"`, `byte_limit: 6000`); open merge requests `list_merge_requests` (`state: opened`).
6. **Finish every answer with the owner's next command** on one line, for example: Next: `sidebar-dev: task 003`.

## Rules

1. English only. First line of every answer: `Domain: <your domain>`. Short and concrete answers; no pasted files or test output.
2. Read `context/<domain>.md` and ONLY the files it lists. If `tools/prompts/domain/<domain>.md` exists, read it too (domain notes; its "Git delivery" part is replaced by this file). Then read the task spec. Do only what the task asks.
3. One task = one branch = one merge request (MR). The branch name is the `Branch:` line of the spec (normally `<domain>/<task>`). Never push or commit to `master`. The `-tdd` agent creates the branch, the `-dev` agent continues on it. Commits reach GitLab with git, or with `add_branch` + `add_commit` (Start here, item 4).
4. Commits read `<type>: <what>` (`test:`, `feat:`, `fix:`, `docs:`). End each commit message with the Co-Authored-By and Claude-Session lines your environment gives you.
5. Change only your domain's files (table: `tools/domains.json`). With a terminal, check before pushing: `node tools/ci-check-pr.js <branch> origin/master` (in a cloud chat the CI job `domain` checks it). Anything outside your domain: write `requests/<from>-to-<to>-NNN-<name>.md` (fits the interface) or `proposals/NNN-<name>.md` (changes an interface) and stop that part. Interfaces and shared files change only with the owner's approval.
6. Log the change in `changes/<domain>.md` in the same merge request (date, what, why, files, how to verify, follow-ups).
7. Tests. In a cloud chat you cannot run them: push, then read the CI result (rule 9). With a terminal, cut the output: `php tests/php/run.php 2>&1 | tail -15`, `php tests/data/run.php 2>&1 | tail -15`, `node tests/js/run.js 2>&1 | tail -15` (`--no-browser` is quicker). Never weaken, delete or edit a test you did not write for this task.
8. Merge request: `save_merge_request` (`project_id`, `source_branch`, `target_branch: master`, `title`, `description` = `.gitlab/merge_request_templates/Default.md` filled in, `squash: true`, `remove_source_branch: true`). The `-tdd` agent opens it right after pushing the red tests, as a **Draft**: title `Draft: test: <what>`. The `-dev` agent works on the same branch; when the newest pipeline is `success`, it removes `Draft: ` from the title (`save_merge_request` with `merge_request_iid` and the new `title`). `gh` and GitHub are not used any more.
9. Check CI: `get_merge_request` (`include: ["pipelines"]`) every 45 s (up to 10 min) until the newest pipeline is not `created`, `pending` or `running`. It must be `success`. On `failed` read `get_pipeline` (`include: ["jobs"]`, `job_status: failed`) and `get_job` (`include: ["log"]`, `from: "end"`, `byte_limit: 6000`), fix on the same branch, push again. A red pipeline is expected on a `-tdd` Draft: only the new tests may fail.
10. **Only `gatekeeper` merges, and never a Draft.** `-dev` agents fix red checks on the same branch, remove the Draft mark, report "MR !n ready for gatekeeper" and stop. Nobody else merges, ever.
